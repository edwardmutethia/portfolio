Project overview

A compact operating system for a coaching business.

CoachFlow is a full-stack MVP for an independent coach who currently has to coordinate a public course page, payment flow, client materials, and sales information across separate services.

The application combines a course storefront, Stripe purchase and subscription handling, client content access, a dashboard, and seeded sales views in one Next.js application. It is intentionally presented as an MVP rather than a finished SaaS launch.

The problem

Important customer context is scattered across disconnected tools.

A coach may have a public page for a programme, a separate payment link, client documents in cloud storage, enrollment information in a spreadsheet, and a calendar for onboarding. The customer journey becomes fragmented, and the coach has no single operational view.

The product question was whether a small, focused application could connect those steps without introducing the complexity of a full learning-management platform.

The users

Two roles with different needs.

  • Coaches publish programmes, collect payments, manage client access, and review sales activity.
  • Clients discover a programme, purchase access, and open the content associated with their enrollment.

The solution

Connect storefront, payment state, and client delivery.

  • Server-rendered course pages present programme content and clear purchase paths.
  • Stripe Checkout handles one-time purchases and subscriptions.
  • Webhook handlers create or cancel enrollment state from verified Stripe events.
  • Client portal access is prepared from the customer email and enrollment relationship.
  • A dashboard brings programmes, clients, sales, and recent activity into one interface.

Engineering

A typed application with explicit payment and data boundaries.

Application stack

The MVP uses Next.js 16, React 19, TypeScript, Tailwind CSS 4, Prisma 7, SQLite through better-sqlite3, Zod, and Stripe. Server actions and route handlers keep mutations close to the data they affect.

Data model

The relational schema represents courses, pricing, customers, purchases, subscriptions, enrollments, and content access. Seeded local data makes the main product flows reviewable without external accounts.

Payment lifecycle

Checkout state is not treated as complete when the browser returns. Enrollment and cancellation behavior is driven by webhook handlers, keeping the local database aligned with verified payment events.

Honest MVP boundary

Coach authentication, a fully integrated booking calendar, and first-party automated tests are not part of the completed implementation. Those gaps are documented rather than hidden behind product claims.

Challenges & decisions

Keep the first version coherent instead of artificially complete.

  • Use relational data to make enrollment and access relationships explicit.
  • Keep Stripe as the payment source of truth and update enrollment from webhooks.
  • Use seeded data to demonstrate complete product states without fabricating customer outcomes.
  • Use email-based portal access for the MVP, then document the need for proper coach authentication.
  • Keep booking as a manual enrollment flow rather than claiming an unfinished calendar integration.

The design decision was to prove the core commerce and delivery loop while making every missing production concern visible.

Results

A working product foundation, not a traction story.

What is evidenced

The repository contains a completed local Next.js build, seeded SQLite data, course pages, checkout and subscription actions, Stripe webhook routes, portal flows, and a dashboard interface.

No public deployment, revenue, customer, conversion, retention, or performance metrics are claimed. The next engineering step would be to add authentication, automated tests, production data storage, and deployment controls before treating it as a live product.
